# samo-radio

samo-radio is Samo's own audio output: a small daemon on a machine with a sound
card, playing whatever Samo tells it to out of a physical socket. In the normal
setup that machine is the server itself and the socket is its line-out, wired
into an amp.

It is two things at once:

- **A station.** It tunes a [channel](channels.md) and stays there. After a
  power cut it comes back on air by itself — nobody has to open an app.
- **A cast target.** "Play to samo-radio" from a phone or the web UI sends a
  queue to it. When that queue runs out, it drops back to the station.

The daemon lives in its own repo: [`samo-radio`](https://github.com/bouliehaan/samo-radio).

## How the pieces talk

```
  client                     samo-server                    samo-radio
    │                            │                              │
    │ POST /api/v1/samo-radio/   │  POST /v1/play               │
    │ devices/{id}/play          │  (items resolved to URLs)    │
    ├───────────────────────────►├─────────────────────────────►│
    │  {type:"track", id:"…"}    │                              │
    │                            │◄──── GET /api/v1/…/stream ───┤
    │                            │      Authorization: Bearer   │
    │                            │      (the device's token)    │
    │                            │                              ▼
    │                            │                        ffmpeg → PCM → 🔊
```

**Clients never talk to a device directly.** Every command goes through Samo,
which forwards it. That is what makes the phone's controls work from outside the
house through the Cloudflare tunnel, and it keeps accounts, sessions and TLS in
one place instead of growing a half-version of each on the daemon.

## Registering a device

1. Install the daemon on the machine with the sound card:
   `sudo ./packaging/install.sh` in the samo-radio repo. It prints a **control
   token** and the list of audio outputs.
2. In Samo: **RADIO → SAMO-RADIO → + ADD DEVICE**. Give it a name, the control
   URL (`http://127.0.0.1:7970` when it is on this machine) and that token.
3. Samo pairs it immediately: it mints an API token, hands it over, and the
   device stores it.
4. Pick the output device and a default station in the device's SETTINGS.

## The two credentials

They point in opposite directions and it is worth keeping them straight:

| | Direction | Purpose |
|---|---|---|
| **control token** | Samo → device | Proves Samo to the daemon. Generated by the installer, pasted into Samo once. |
| **device token** | device → Samo | A real `users.tokens` row so the device can pull audio. Minted at pairing, revoked when the device is deleted. |

The device token belongs to the reserved `user-server` account rather than to
whichever admin clicked PAIR, so the device keeps working after that person's
tokens are rotated, and it never shows up in a human's token list to be revoked
by someone wondering what it is.

## Where the device fetches audio from

Two base URLs are in play and mixing them up is the bug to avoid.

- **Stream URLs** are built on the device's `stream_base_url`, which defaults to
  this server's own listen address on loopback. The device is next to the
  server; a phone pairing over the public tunnel must not send it off to fetch
  audio through Cloudflare and back.
- **Artwork URLs** are built on the requesting client's host, because the client
  is the one that renders them and may be anywhere.

`resolveSamoRadioItem` in `internal/api/samo_radio_handlers.go` is where both are
produced, and `samo_radio_handlers_test.go` pins the distinction.

## What can be sent

Clients send catalog **ids**, never URLs. The mapping from an id to a stream URL
exists once, on the server, and a client cannot ask the device to fetch an
arbitrary address.

| `type` | resolves to |
|---|---|
| `track` | `/api/v1/music/tracks/{id}/stream` |
| `episode` | `/api/v1/podcasts/episodes/{id}/stream` |
| `audiobook` | `/api/v1/audiobooks/{id}/stream` |
| `file` | `/api/v1/media/files/{id}/stream` |
| `station` | `/internet-radio/{id}/stream` (live) |
| `radio` | `/radio/{id}/stream` (live) |

Channels are not items: they are a mode. `{"mode":"channel","channelId":"…"}`
tunes the device instead of queueing anything.

## Levelling

Resolved items carry `gainDb` (and, rarely, `limitPeaks` + `ceilingDbtp`)
alongside the stream URL. The device applies the gain as a constant offset in
its decode chain; it does no measuring and makes no level decisions of its own.

The split is the same one as for URLs. The gain comes from an EBU R128
measurement of the file, which needs the library, a cache and a machine willing
to spend CPU on analysis — none of which belong in a process whose one job is
keeping the sound card fed. See `docs/channels.md` for the policy, and
`internal/loudness` for why the gain is a constant rather than a compressor.

Two consequences worth knowing:

- A queue is resolved **once**. If a track has never been measured, that queue
  plays it at its native level and the measurement lands for next time — which
  is the main reason the server backfills the library in the background rather
  than relying on warm-ahead.
- Measurement reads the file on disk, not the stream URL handed to the device.
  Same bytes, no HTTP, no token, and the server does not serve itself a request.
- Live items (`station`, `radio`) carry no gain. Tuning the device straight at
  an internet station is the one playback path with no levelling; inside a
  channel's rotation, live sources *are* levelled by the channel streamer.

## API

Listing, status and transport are open to any signed-in user — "play it in the
kitchen" is no more privileged than playing it on your own phone. Registration
and configuration require admin.

| Method | Path | Notes |
|---|---|---|
| `GET` | `/api/v1/samo-radio/devices` | Each row carries the device's live state |
| `POST` | `/api/v1/samo-radio/devices` | admin |
| `GET` | `/api/v1/samo-radio/devices/{id}` | |
| `PATCH` | `/api/v1/samo-radio/devices/{id}` | admin |
| `DELETE` | `/api/v1/samo-radio/devices/{id}` | admin; revokes the device token |
| `POST` | `/api/v1/samo-radio/devices/{id}/pair` | admin |
| `GET` | `/api/v1/samo-radio/devices/{id}/state` | |
| `GET` | `/api/v1/samo-radio/devices/{id}/outputs` | admin; enumerates sound cards |
| `PATCH` | `/api/v1/samo-radio/devices/{id}/settings` | admin; output, default station |
| `POST` | `/api/v1/samo-radio/devices/{id}/play` | queue or channel |
| `POST` | `/api/v1/samo-radio/devices/{id}/{pause,resume,next,previous,stop,standby}` | |
| `POST` | `/api/v1/samo-radio/devices/{id}/seek` | `{positionSeconds}` |
| `POST` | `/api/v1/samo-radio/devices/{id}/volume` | `{volume}` 0–1 |

`stop` ends the ad-hoc queue and hands the aux port back to its station;
`standby` is the real off switch. Both exist because "stop this podcast" and
"silence the room" are different intentions on a device whose job is to always
be on air.

Every command returns the device's new state, so a client never has to follow
one with a fetch.

## An unreachable device is normal

A device that is off, unplugged or mid-reboot still appears in the list — with
no `state` and a `lastError` explaining why. Listing fetches every device's
state concurrently with a 3-second deadline and folds failures into the row, so
one dead device never blanks the panel or stalls the page.

## Implementation notes

- **Package**: `internal/samoradio` owns devices, credentials and the HTTP
  conversation. It knows nothing about the catalog — turning "play this album"
  into playable items is `internal/api`'s job, where the catalog already is.
- **Token minting** goes through a narrow `TokenMinter` interface so the package
  never has to import `internal/users`; `SamoRadioTokenMinter` in
  `internal/api/samo_radio_tokens.go` is the adapter.
- **Migration**: [`migrations/postgres/0012_samo_radio_devices.sql`](../migrations/postgres/0012_samo_radio_devices.sql).
- **Web UI**: `web/src/ui/samo_radio.js`, mounted as the third sub-mode of the
  RADIO tab.
